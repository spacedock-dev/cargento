## Problem

Its replacement orders exact questions before native input signals, so the question's rounded age cannot cross a gate's timestamp. Recommend crediting the visible behavior to existing merges #245/#247, correcting only the surviving design-note drift, and then reconciling DRC-4199. Do not add `asked_at` to deliver a property already satisfied. A records-only closure is possible only if the captain explicitly defers the remaining original documentation criterion; this report does not silently drop it. The smallest complete path is a documentation-only implementation after the gate approves the draft below, followed by the normal verification/merge/receipt stages.

Rejected alternative: implementing absolute timestamps and restoring chronological interleaving would change today's question-first policy, require payload and byte-pin work, and deliver no demonstrated missing user value. A new chronology policy would need a separately authorized product decision; none is made here.

### Original issue description (verbatim)

````markdown
## User value

A person watching the gate queue notices this once two waits that began within half a second of each other stop swapping places on every poll. P3, keep: without an absolute timestamp for a question, the queue's own claim to be ordered by what needs you most is untrue on every tie this close.

## What needs to be done

`waitingQueue()` ranks a gate against a question by when each wait began. A gate carries an absolute `blocked_since`; a question does not, so the page reconstructs its start from `age_sec`, a whole number rounded from a float clock that drifts between polls. When a gate and a question began within roughly half a second of each other, the reconstructed order flips between consecutive polls even though nothing about either wait changed. Frontend-only fixes were tried and rejected: quantising the gate's timestamp just moves the churn, a sticky order needs state the queue deliberately avoids, and widening the tie-break window would misorder pairs that are genuinely a second apart.

Fix scope: publish an absolute epoch for a question, `asked_at` beside the existing `age_sec` in `_ask_cards` (`aggregate.py`), and rank on `asked_at` in `waitingQueue()`. Keep `age_sec` for the card's relative display. This is a payload-contract change; check what pins the ask-card shape before changing it.

Acceptance criteria:

* A question carries an absolute start in the payload and `waitingQueue()` ranks on it.
* A test drives three consecutive polls with a gate and a question sub-second apart and asserts the order is identical in all three.
* The tie-break note in `docs/design-ask-lane.md` is corrected where it implies the existing fixed tie-break rule covers this case.
````
