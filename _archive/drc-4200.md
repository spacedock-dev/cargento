## Proposed approach

Use the existing documentation-test integration for the authorized standing corpus privacy assertion and negative path fixture. Define permitted string roles from the capture contract: schema/type names, harness/tool and explicitly admitted closed vocabularies, pseudonymous markers, timestamps/versions, and recorder-authored arrangement/provenance or measured verdict explanations. Validate role and content together: a provenance key alone never exempts a string from the exclusion of concrete personal paths, email addresses or captured prompt/tool content. Keep documented recorder command/API identifiers distinct from captured filesystem values through narrowly reviewed role/literal cases; do not whitelist a whole file or its entire note field.

For the two named captures, retain measured fields, record ordering, arm identities, verdicts, timing and unmeasured caveats. Remove or shape-reduce only content actually demonstrated to cross the boundary; do not fabricate removal receipts. Current evidence supports retaining their payload bytes and adding an accurate provenance audit note, unless implementation's role audit identifies a concrete exclusion. Preserve the original allegations as dated history in the issue. Assertions must report repository-relative capture name, row and a safe reason, never the rejected value or an untrusted key containing it.

This is proposed, not silently settled. The standing assertion and negative path deliverable were expressly commissioned and need no additional authorization. If role review uncovers an ambiguous new payload-value exception, return that question to the first officer; do not grandfather it from its presence in the corpus.
