## Proposed approach

Recommend one typed **"Alert once when an observed entity enters [stage]"** condition per exact Spacedock workflow. The first qualifying entity trips that rule; later entities do not repeat it until the reader explicitly chooses Rearm. This is a change in observed frontmatter status, not proof that a worker started, finished, or stayed within a boundary. The alternative of an alert on every displayed stage refresh is smaller but cannot distinguish first sight, stale boot state or inactive worker labels from new work. A repeating per-entity engine adds state and alerts without being needed for the stated value.

### Identity and supported evidence

- Derive a full opaque SHA-256 identity from a versioned, unambiguously encoded pair of canonical workflow-definition and entity-state directories. Include both: split-root state can move independently. Publish/store only the digest, safe workflow name and bounded stage identifiers, never the paths. It survives a session change or dashboard restart at those same directories; moving either is a different workflow requiring a new declaration. An identical directory pair reported by multiple sessions is one source, evaluated once per collection.
- The selector is attached to a source-backed workflow card in Course and includes the workflow name, available goal and source session label. If two candidates remain indistinguishable to the reader at that scope, refuse to arm and say `Workflow choice is ambiguous; open one source session or give the workflows distinct names.` Never silently choose the first. The backend still rejects cross-binding even when names match; the digest is not a credential or proof of human identity.
- Use only a successful, bounded, currently revalidated entity frontmatter read for evaluation. Carry `source=entity-state`, `source_written_at`, `observed_at`, and `stage` with each qualifying observation, plus its opaque workflow identity and entity slug. A stat time is a file-write time, not a transition timestamp. Cache reuse requires the existing stat/file-identity checks; missing, unreadable, stale, future-dated, unknown-stage, capped or disabled evidence is unavailable, not unchanged.
- Keep the current frontmatter-only discriminator, regular-file/symlink/identity checks, split-root rules and caps: 64 KiB README, 8 KiB entity, 400 frontmatter lines, 32 declared stages, 96 entity files and 8 workflows per session. Include valid initial/terminal states for baselines; the 12-row display cap must not silently become the evaluation population. Publish how many entity records were evaluated and state partial coverage when bounded enumeration omits any; a missing entity baseline is dropped, never interpreted as a stage change.
- Add Codex attachment by invoking the existing incremental boot reader on collected rollouts. Preserve direct Claude/Pi/Codex output support. For the newly measured Codex form only, accept one complete JSON fulfilled-result object containing `value.exit_code=0` and string `value.output`; that string must be the complete boot object. Stay inside the existing tool-result provenance boundary, scan-byte limit, candidate/record limits and one extra decoding layer. Reject failed/rejected/nonzero, quoted conversation, nested decoys, incomplete/truncated and over-depth wrappers. Do not search arbitrary nested strings, command arguments, dispatch files, or repository bodies for a path.
- Codex support is a required C1 capability, not a promise already shipped. Claude and Pi keep their existing boot-derived coverage; other harnesses or unsupported wrappers show `Workflow stage source unavailable`. Discovery-only workflow definitions do not authorize entity reads or monitoring. `--no-spacedock` disables boot/project reads and evaluation; stored rules remain visible as not monitoring.

### Declaration, baseline and rearm semantics

- Store one rule per identity in a separate versioned `~/.cargento/cargento-tripwires.json`, following E6's server-owned clock, bounded JSON, 0600 atomic replacement and error handling. Do not change the dismissal file schema. Rule state is `armed` or `tripped`; a saved revision, chosen stage and one optional trip record are durable. Removal is explicit. Session `/clear`, marking handled, page reload and a new session at the same workflow do not remove or rearm it.
- Reject the 65th rule with a readable capacity message; do not expire or evict a future declaration. Limit each in-memory baseline to the existing 96 entity budget and clear absent entries each collection. No per-entity durable history, automatic rearm, free text parser or polling subprocess is added.
- Saving/rearming captures a fresh baseline but never fires. First observation at the target says `Already at [stage]; entry was not observed.` First observation elsewhere says `Baseline recorded; watching for entry into [stage].` With none: `Saved; waiting for current entity state.` A newly seen entity follows the same first-observation rule.
- For an armed rule, two consecutive eligible observations of the same workflow/slug must have different statuses, with the newer equal to the selected stage and a later source-write time. Only then record `Observed [entity] change from [before] to [stage]` with both observation times. Other→other, repeated target, unknown→target, and missing→target never fire. A skipped target is never inferred from stage order: workflows can branch and loop.
- Restart, a failed/missing source, a source identity/taxonomy change, backward clock or a collection gap longer than twice the configured reconcile interval resets baselines. Default gap bound is 60 seconds, derived from the current 30-second reconcile interval; it is an observation-continuity bound, not an alert-latency guarantee. First reacquisition says `Observation resumed; baseline reset. Changes during the gap were not checked.` A removed selected stage suspends the rule until it is explicitly edited; reordering/changing the taxonomy resets its baseline.
- Persist the trip latch **before** requesting a notification. If persistence fails, do not claim a saved rule or send a repeat-prone popup; show `Could not save the trip; notification was not attempted.` Retry the pending observation on a later successful save without advancing its baseline past it. If the process exits between latch and notification, retain the trip and say the attempt is unrecorded; do not automatically replay it on restart. Rearm creates a new rule revision and new baseline, including if an entity remains at the target.
- A corrupt, truncated, over-cap or unrecognized-version store suspends monitoring and displays `Saved tripwires could not be read; no stage conditions are being checked.` Do not silently treat unreadable durable intent as an empty healthy list or overwrite it during collection. A failed create/edit does not optimistically change the UI. A `--no-tripwires` switch prevents all reads/writes of this store and removes mutation controls; `--no-spacedock` leaves the store readable but all rules suspended.

### Notification and UI semantics

The board records the trip independently of whether a session is visible or a notification lane exists. Course exposes the typed stage selector, Save, Rearm and Remove; Projects keeps the saved-rule list reachable after all sessions leave. Each rule shows its scope, selected stage, armed/tripped/unavailable status, baseline or trip evidence, and current coverage. Counts derive from the rule/entity rows rendered. Preserve keyboard focus, input selection, unsaved stage choice and save/error cues across normal redraws; do not re-create the old free-text editor as an executable surface.

Reuse the injected native notifier and `deliveries.record` lane/outcome vocabulary; use a dedicated stage-tripwire event id derived from rule id and saved revision, not the session's gate state. The browser lane receives new event ids through the current leader/priming notification path, dedupes them for that tab lifetime, and remains silent when the native backend owns notifications. Opening/reloading a tab on an existing trip does not pop it again. A no-lane or rejected permission state leaves the trip visible, stating the absence. Mac service acceptance means the service accepted a request, never that a banner appeared or someone saw it; the page may report a lane, never a delivery.

Within one server, serialize a rule's read/update/claim so simultaneous collection/request paths cannot spend it twice. Reuse the existing **disclosed** multi-server file model: simultaneous dashboards can lose a write or duplicate an alert under last-writer-wins. This proposal does not promise global exactly-once delivery or add cross-process locking. Persistence suppresses a normal restart replay; no crash-proof delivery guarantee is offered. Request bodies carry rule action, exact published identity, stage and expected revision only; no client time, path, regex, prose or executable instruction. Use strict local-origin/body bounds and reject unknown fields and stale revisions.
