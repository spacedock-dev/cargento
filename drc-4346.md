[DRC-4346](https://linear.app/recce/issue/DRC-4346) — A teammate blocked on its own workers reads inactive while those workers run, because a grandchild's activity never reaches its parent or the lead

## User value

A person watching a workflow whose reviewer has fanned out lenses sees the reviewer active while its lenses work underneath it, and the lead session reads working rather than idle. P2, sharpen: **the board accurately reflects when a teammate and lead are active because workers are running.**

## Problem

In `collectors/claude.py`, teammate liveness and lead activity sources only check `c["mtime"]` of the teammate's own transcript. When a teammate dispatches workers and waits on them, its transcript is quiet (> 90s), but its workers' transcripts are actively updating (< 90s). Consequently, the teammate is marked `active: false` in the published roster, excluded from `subagents`, and the lead session's activity sources omit the grandchild writes, leaving the lead session reading `idle` ("awaiting your message") despite active work underway.

## Proposed approach

1. In `cargento/skills/cargento/cargento_runtime/collectors/claude.py`:
   - Discover grandchild transcripts for each child via `agent_transcripts(c["path"])`.
   - Determine teammate liveness: a teammate is live if its own transcript is fresh OR if any of its grandchild workers are fresh (unless demoted by `member_flags`).
   - Determine teammate effective mtime: max of its own mtime and its grandchild workers' mtimes.
   - Include live teammates in `subagents` so `state_detail` reflects the running teammate and lead session derives `state: "working"`.
   - Absorb grandchild mtimes into `activity_sources` (`latest_grandchild_file_mtime`) so `last_activity` reflects worker progress.
2. In `cargento/skills/cargento/tests/test_claude.py`:
   - Add unit tests verifying a teammate with live workers reads as `active: True`, its worker is attributed with `parent`, and the lead reads as `working`.
   - Verify parked teammates with no live workers remain `active: False` and do not make lead read as working.
3. Run full pre-PR verification suite.

```markdown
## User value

A person watching a workflow whose reviewer has fanned out lenses sees the reviewer greyed out as not running while its lenses are visibly working underneath it, and the lead session above them both reads idle. The board is no longer lying by omission — the teammate-visibility fix made the workers visible — but it is now telling a smaller lie about who is busy. P2, sharpen.

## What was measured, 2026-09-03

Reproduced during the teammate-visibility fix's own review, on the live board: a teammate quiet for 300 seconds, its worker written to 2 seconds earlier. Published result: the teammate active false, the worker active true attributed to it, the lead session idle.

This is not a violation of that fix's acceptance criteria. Its AC-2 asked that a quiet teammate read as distinct from a running one, and AC-4 froze the state derivation byte for byte so that a parked child could never make its lead read as running (the rule DRC-4118 and DRC-4263 both bind). Both hold. What is left is the case neither criterion covers: a child that is quiet only because it is waiting on its own children.

## The two mechanisms weighed, and why neither shipped in that fix

Marking the teammate live whenever any of its workers is live is the cheap change and the worse one: it puts an active pill under a lead that still reads idle, so the row contradicts its own detail.

Absorbing a grandchild's transcript mtime into the session's activity sources is the consistent change. It is what DRC-4118 does for Cursor's flattened subtree and what the lead's own agents already do through the latest agent-file mtime. It is also a change to the state derivation, the field AC-4 froze, so it needs its own acceptance criterion and the captain's ruling to reopen that field. The promote condition on the deferred item: a lead that reads idle for as long as a teammate is blocked on live workers.

## What a fix must cover

* A lead whose teammate has a live worker reads as working, with the state detail naming the teammate and the worker.
* A teammate with a live worker reads as running, with the worker attributed.
* A parked teammate with no live worker still reads as not running, so DRC-4118's and DRC-4263's rule is not weakened.
* The state derivation change is declared as such, with the pre-change and post-change payloads compared on live stores the way the visibility fix compared them.

## Out of scope

Turn progress, ETA or token totals on a teammate's pill. Nested pane teammates, which are a separate finding.
```

## Acceptance criteria

**AC-1 — Teammate with live workers reads as running** (offline)
Verified by: `session["subagents"]` contains teammate with `active: True` when its grandchild worker has a fresh mtime even if the teammate's own transcript is stale (> 90s).

**AC-2 — Worker is attributed to the running teammate** (offline)
Verified by: `session["subagents"]` contains grandchild worker with `parent: <teammate_name>` and `active: True`.

**AC-3 — Lead session reads as working when grandchild is active** (offline)
Verified by: `session["state"] == "working"` and `session["state_detail"] == "running 1 subagent"`.

**AC-4 — Parked teammate with no live workers reads as not running** (offline)
Verified by: `session["subagents"]` contains teammate with `active: False` when both teammate and worker transcripts are stale, and lead reads `session["state"] == "idle"` if no other agents are running.
