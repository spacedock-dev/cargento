### Original issue body — DRC-4380 — 2026-09-15

## User value

A person running a Pi session notices this when a standing prompt puts that session in the gate queue instead of leaving the board unable to say either way. P3, sharpen: gate detection reaches Pi, on a documented event pair rather than an inferred one.

## Why this exists, and what it replaces

[DRC-4190](<https://linear.app/recce/issue/DRC-4190/b2g-pi-does-anything-fire-while-pis-own-approval-prompt-stands>) (B2g) asked "does anything fire while Pi's own approval prompt stands?" **Pi has no approval prompt**, so that question has no subject and the issue is closed as refuted at its premise. This issue is the question that survives it.

Pi's own documentation settles both halves:

* **No built-in per-tool gate.** `project_trust` is the only standing prompt Pi raises on its own, it fires once per directory rather than per tool call, and the docs are explicit that it "is only an input-loading guard. It prevents a repository from silently changing pi's settings or extensions before you approve it. It does not make untrusted code, untrusted prompts, or untrusted model output safe." An approval gate on Pi is something an extension implements through `tool_call` returning `{ block: true }`, which is what the third-party forks do.
* **But Pi documents a waiting-for-user signal, and it is the cleanest on the board after OpenCode's.** `ui_prompt_start` and `ui_prompt_end` fire around `ctx.ui.select()`, `ctx.ui.confirm()`, `ctx.ui.input()`, `ctx.ui.editor()` and `ctx.ui.custom()`, and the docs say why in the vendor's own words: so that "host/status integrations can report 'waiting for user' instead of just 'running'". `ctx.sessionManager.getSessionId()` supplies the key.

So Pi's registry row is correctly `False` today, and the reason on the board should be "we ship no adapter", not "no signal exists".

## What needs to be done

Route 1, a bundled adapter, the same class as the OpenCode build:

* A TypeScript extension bundled under `cargento/skills/cargento/` for `~/.pi/agent/extensions/`, subscribing to `ui_prompt_start` and `ui_prompt_end` and posting them with `getSessionId()`.
* `EVENTS_BY_HARNESS` gains the Pi table mapping the pair to `input_requested` and `input_resolved`.
* `IDENTITY_NORMALIZERS["pi"]`, keyed to whatever `collectors/pi.py` already keys on.
* Flip the registry row, proved by <issue id="e8ccc627-2344-44b4-b51f-1aa30ab27b7c" href="https://linear.app/recce/issue/DRC-4378/restore-the-reports-needs-input-oracles-and-the-comment-that-claims">DRC-4378</issue>'s restored derivation.

## What must be measured before it ships

`ui_prompt_start` is documented and unmeasured here. **Pi is not installed on this machine** and no loopback stand-in exists in this repository, so a capture costs a contained install plus a stdlib OpenAI-compatible server before the first datum. Record to `docs/captures/pi/`, and do not flip the flag on documentation alone.

The pair fires around **any** UI prompt, which on stock Pi means `project_trust` and nothing else. Whether a once-per-directory trust prompt should raise a gate row, or be filtered, is part of this issue.

## Acceptance criteria

* **User-visible:** a Pi session held at a prompt appears in the gate queue as Needs input, and clears when it is answered. **Verified by:** drive one Pi session to a prompt with the extension installed.
* The flip is proved by derivation rather than declared. **Verified by:** <issue id="e8ccc627-2344-44b4-b51f-1aa30ab27b7c" href="https://linear.app/recce/issue/DRC-4378/restore-the-reports-needs-input-oracles-and-the-comment-that-claims">DRC-4378</issue>'s oracle.
* A capture under `docs/captures/pi/` carries the measured event shape, not the documented one.
