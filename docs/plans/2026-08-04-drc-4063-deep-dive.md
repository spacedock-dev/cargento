# Deep dive: DRC-4063, the Codex usage tile

## Issue summary

Publish Codex quota on the dashboard from the `rate_limits` snapshots the Codex CLI already
writes into its session files. No network, no credential, both SECURITY.md invariants untouched.
This is the first collector to fill the `usage` payload contract that DRC-4062's band renders.

## Classification

**Type:** feature (backend collector extension; the frontend shipped in DRC-4062)
**Priority:** High
**Branch:** `feature/drc-4063-usage-tile-codex-quota-from-disk-option-d` (not created yet)

## Current state

- Disk-verified event shape: `token_count` events carry `payload.rate_limits` beside
  `payload.info`, with `primary` / `secondary` window objects (`used_percent`,
  `window_minutes`, `resets_at` epoch) plus `plan_type` and a `credits` block. On a `prolite`
  plan only the weekly window exists (`secondary: null`), so windows must be mapped by
  `window_minutes`, never by position, and an entry may carry one window.
- `transcripts.analyze_codex_transcript` already iterates exactly these events (it reads
  `last_token_usage` for the rate figures) over a bounded `read_tail`.
- `collectors/codex.py` scans rollout files, calls the analyzer for active sessions, and keeps
  per-session results; the newest snapshot across analyzed files is the natural harvest point.
- `aggregate.Application.collect()` assembles the payload behind a per-harness failure boundary
  driven by the `HarnessSpec` registry; the top-level `usage` key belongs here.
- The frontend (shipped) renders `d.usage` entries `{harness, state, asOf, fiveH, week, ...}`,
  shows the band only when the key exists, tolerates missing windows, and shows an empty state
  for a present-but-empty list.

## Key files

| File | Role |
|------|------|
| `cargento_runtime/transcripts.py` | Analyzer gains `rate_limits` capture (newest in tail). |
| `cargento_runtime/collectors/codex.py` | Harvest newest snapshot, map windows, format resets. |
| `cargento_runtime/aggregate.py` | Optional per-spec usage provider; top-level `usage` key. |
| `tests/test_codex.py`, `tests/test_transcripts.py` | Fixture-driven coverage. |

## Acceptance criteria

1. A rollout fixture with `rate_limits` yields a `usage` entry: `harness: "codex"`,
   `state: "ok"`, `asOf` = the snapshot event's epoch, windows mapped by `window_minutes`
   (under a day to `fiveH`, a week and over to `week`), integer percents, short reset text.
2. The newest snapshot wins across files and within a file's tail.
3. A payload on a machine with a Codex store carries `usage` (possibly empty); a machine
   without Codex carries no `usage` key and the dashboard is byte-identical to today.
4. Malformed and missing `rate_limits` (nulls, absent windows, absent `resets_at`, string
   percents) degrade to omission, never to a collector error; a broken usage read must not
   take the Codex session rows down with it.
5. Reset text formats locally: same day as "HH:MM", within a week as "Thu 09:00", further out
   as a date.
6. Coverage threshold holds; the quality gate passes; no SECURITY.md or version-field changes.

## Risks and open questions

- Only active sessions' tails are analyzed, so a machine idle past the window shows the store
  discovered but no snapshot: the band's empty state covers it honestly.
- `read_tail` bounds the scan; a tail with no `token_count` event yields no snapshot. Frequent
  token events make this rare, and staleness is visible via "as of" when it happens.
- The `credits` block and `plan_type` do not fit the contract's extras (burn/today/cost) and
  stay unpublished; a later ticket can extend the contract if wanted.
- Timezone for reset text is the server's local zone, same as every other time on the page.
