# Deep Dive: DRC-3987 — Add Support for Pi

Issue: [DRC-3987](https://linear.app/recce/issue/DRC-3987/add-support-for-pi)

## Issue Summary

Pi sessions are not currently visible in Cargento. The Linear issue contains one sentence of
product scope — “Pi is not currently supported in cargento” — and the Slack-synced discussion
confirms that support has not yet been added. It does not define what “support” means, so this
document derives acceptance criteria from Cargento's existing harness contract and Pi's current
on-disk format.

The proposed scope is **monitoring Pi sessions in the existing dashboard**. It does not add a Pi
installation package for the Cargento skill. The repository currently packages Cargento for
Codex, Claude Code, Antigravity/AGY, and Gemini CLI; that distribution surface is separate from
the set of harnesses whose sessions Cargento can observe.

## Current State

Cargento currently registers and documents eight monitored harnesses: Claude Code, Codex,
Gemini CLI / Antigravity CLI, GitHub Copilot CLI, OpenCode, Cursor CLI, Goose, and Factory Droid.
Pi has no store root, metadata parser, transcript analyzer, turn classifier, collector, registry
entry, diagnosis entry, or client-side harness label.

Pi's current upstream contract is:

- The latest release reviewed is
  [v0.82.1](https://github.com/earendil-works/pi/releases/tag/v0.82.1), published 2026-07-25.
- By default, sessions are append-only JSONL files under
  `~/.pi/agent/sessions/--<encoded-cwd>--/<timestamp>_<uuid>.jsonl`.
- The first record is a versioned `session` header with the session `id`, `timestamp`, and `cwd`.
  Later records form a tree using `id` and `parentId`; `message` records wrap user, assistant,
  and tool-result messages. Assistant messages include output-token usage, and assistant content
  can contain `toolCall` blocks. The authoritative schema is Pi's
  [session format](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/session-format.md).
- The current conversation is the ancestor path from Pi's current leaf, not every entry in the
  file. Cargento can reconstruct the best persisted approximation from the last appended entry;
  a branch navigation that appends nothing leaves no passive signal.
- A later `session_info` record can set or clear the session name. The latest such record wins.
- Header `parentSession` means that a session was forked or cloned from another session. Pi core
  does not use it as a subagent-parent relationship, so Cargento must not fold these sessions
  together.
- `PI_CODING_AGENT_DIR` relocates Pi's configuration directory, while
  `PI_CODING_AGENT_SESSION_DIR` relocates the session store. The latter is a directory containing
  JSONL files directly, unlike the nested default store. Pi documents both in its
  [environment-variable reference](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/environment-variables.md).
- Pi also supports a `sessionDir` setting, with command-line `--session-dir` taking precedence
  over the environment and settings. Relative settings paths resolve from the settings file; see
  Pi's [settings reference](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/settings.md).

No Pi installation or session store is present on the development machine, so implementation
tests must use synthetic fixtures that reproduce the documented v3 format. No user transcript
data needs to be copied into the repository.

## Key Files and Integration Points

### `cargento/skills/cargento/server.py`

- `STORE_ENV_VARS`, `resolve_store_roots()`, `STORE_ROOTS`, and the module-level store constants
  own cross-platform path resolution and diagnosis overrides.
- `first_line_meta()` is the existing bounded, cached seam for immutable JSONL headers.
- `analyze_*_transcript()` functions extract the title, last prompt, token events, last tool, and
  latest plausible event time from transcript tails.
- `_turn_signal()` and `scan_turns()` incrementally track prompt boundaries without re-reading
  whole JSONL files.
- `base_session()`, `rate_from()`, `working_detail()`, and `turn_progress()` provide the common
  dashboard model.
- `collect_*()` functions discover files, deduplicate logical sessions, apply the activity
  window, and assemble rows.
- `HARNESSES` controls discovery and collection. `store_primaries()` and `diagnose()` explain
  searched paths and swallowed collector failures.
- The embedded `HARNESS` JavaScript map supplies the Pi label and `PI` monogram. A custom icon is
  optional because the UI already has a monogram fallback.

### `cargento/skills/cargento/tests/test_server.py`

The existing suites cover store resolution on all supported operating-system path flavors,
metadata parsing, analyzer behavior, incremental turn scanning, collectors, registry isolation,
diagnostics, and embedded client contracts. Pi needs equivalent fixtures and adversarial cases,
not only a happy-path collector test.

### Owned documentation

- `cargento/skills/cargento/SKILL.md` owns the shipped list of monitored harnesses and store
  relocation variables.
- `README.md` owns the front-door count and capability summary.
- `COMPATIBILITY.md` owns cross-harness limitations and path support. It already mentions Pi in a
  Spacedock limitation even though Pi is not collected; that sentence must be reconciled with the
  new support rather than copied forward unchanged.
- The four manifest descriptions and the Codex `interface.longDescription` enumerate monitored
  harnesses and must add Pi. Durable design docs that say “eight harnesses” must likewise move to
  nine.

Manifest **version fields** remain release-workflow-owned and must not change.

The closest repository precedent is commit `d6f72ed` / PR #7. Adding Goose there extended the
platform resolver and diagnostics together with the registry, then exercised fresh, stale,
absent, future-dated, corrupt, hostile-path, and multi-root behavior using synthetic fixtures.
Pi should meet that contract rather than landing as an isolated collector.

## Derived Acceptance Criteria

Because Linear provides no explicit criteria, the following need confirmation before
implementation:

1. Cargento discovers valid Pi v3 sessions in both the nested default layout and a flat custom
   session directory.
2. A Pi row uses the header session ID and `cwd`, derives the project with Cargento's shared
   project rule, and falls back safely when optional or malformed fields are absent.
3. The latest `session_info.name` is the preferred title. Clearing the name restores the first
   meaningful user prompt as the title, even when the relevant `session_info` record is outside
   the transcript tail window.
4. The analyzer reconstructs the branch ending at the best persisted current leaf and excludes
   sibling/abandoned branches from the last prompt, current tool, usage rate, turn history, and
   ETA. User `message` records on that branch start turns; assistant and tool-result records do
   not. The scanner survives files larger than its bounded forward-read window.
5. Output usage from assistant messages, nested tool-result work, compactions, and branch
   summaries drives the recent output-token rate. `toolCall.name` drives the working detail, and
   text/image/tool-result message shapes are handled defensively.
6. Working/idle state and the active-window filter use plausible event and file timestamps, so a
   future-dated or malformed record cannot pin a session as active.
7. Files are deduplicated by logical session ID and the newest copy wins. Partial lines, corrupt
   JSON, non-session JSONL files, unreadable files, and one broken Pi session cannot break Pi's
   remaining sessions or any other harness.
8. `PI_CODING_AGENT_SESSION_DIR` takes precedence over `PI_CODING_AGENT_DIR`, and an environment
   override is authoritative rather than silently mixed with stale defaults. A discoverable
   global `sessionDir` setting is honored with its documented relative-path semantics.
9. Pi fork/clone sessions remain independent dashboard rows. `parentSession` must never create a
   subagent pill or transfer activity/rate to another row.
10. Pi appears in both display modes, the discovered-harness strip, and `--diagnose`, using the
    `PI` monogram when no icon is supplied.
11. Documentation, durable design notes, the four manifest descriptions, and the Codex long
    description name Pi as the ninth monitored harness and state the honest limits:
    Cargento cannot discover arbitrary per-invocation `--session-dir` values or project-local
    `.pi/settings.json` files from a separate process unless the effective directory is also
    exposed through `PI_CODING_AGENT_SESSION_DIR`.
12. The feature does not claim Pi support for needs-input detection, Spacedock workflow
    cartography, or core subagents; Pi does not persist equivalent passive signals.
13. The full canonical pre-PR suite passes on the designated Linear branch without changing
    plugin versions or lowering coverage.

## Risks and Open Questions

### “Pi support” can mean two different products

Monitoring Pi's session store is consistent with Cargento's harness registry. Packaging the
Cargento skill for Pi is a separate distribution project with different manifests and install
instructions. The latter should remain out of scope unless explicitly requested.

### Custom session directories are only partly discoverable

The default store, Pi's two environment variables, and the global settings file are observable.
A separate Cargento process cannot infer a one-off `pi --session-dir ...` argument or search every
project on disk for `.pi/settings.json`. Treating only the default nested glob as “support” would
also be incorrect: the documented custom directory is flat.

### Session names are not immutable metadata

The first-line cache can hold the header, but it cannot own `session_info.name`: names may be
added, changed, or cleared later. A tail-only analyzer can miss an older name after the file grows
beyond `TAIL_BYTES`. Name extraction therefore needs its own append-aware or reverse-scan cache,
with tests that place the winning record outside the tail.

### One file contains mutually exclusive branches

Feeding every Pi record into Cargento's linear JSONL analyzer would select prompts, tools, tokens,
and turn boundaries from abandoned sibling branches. Pi computes context by walking from the
current leaf to the root. The on-disk file does not persist a leaf-only navigation until another
entry is appended, so Cargento can reproduce the last appended branch exactly but must document
the navigation-only blind spot. This needs a Pi-specific branch-aware scan rather than a new
condition in the otherwise-linear generic scanner.

### File activity may lag generation

Pi exposes persisted messages, not a guaranteed streaming heartbeat. A long model response that
writes no intermediate tool call may cross Cargento's 90-second working threshold and briefly
appear idle. This is an upstream observability limit, not a reason to invent activity.

### `parentSession` is actively misleading for subagent logic

It is tempting to reuse the Claude/Codex parent-child assembly because the field name resembles a
thread parent. Pi uses it for forks and clones. Folding on it would hide valid sessions, attribute
tokens to the wrong row, and violate the user's mental model.

### The fixture is contract-derived

There is no local real-world Pi transcript to compare against. Tests should stay close to the
official v3 examples and use permissive parsing around optional fields. The implementation should
also record swallowed Pi read failures in diagnostics so format drift is visible.

## Approaches Considered

### Recommended: a branch-aware Pi adapter inside `server.py`

Add Pi-specific store, metadata, branch-scan, analyzer, and collector helpers beside the existing
JSONL harnesses. Feed their results into Cargento's shared session, rate, state, and rendering
helpers. This preserves the stdlib-only single-file server and gives Pi's tree semantics one
explicit boundary.

### Rejected: treat Pi as Droid with renamed fields

Droid's transcript is linear. Pi stores mutually exclusive branches in one file and moves its
logical leaf backward before appending a new branch. A linear tail parser would be smaller, but it
would report abandoned prompts, tools, tokens, and turn durations as current activity.

### Rejected: shell out to Pi for session discovery

Pi's own session manager understands settings and branch context, but invoking it would add a
Node/CLI runtime dependency, execute user-installed extension code, and make an absent Pi binary
an error rather than an undiscovered harness. Cargento's collectors read local stores passively
and use only Python's standard library; Pi should keep that contract.

## Proposed Approach

1. Update `main` and create Linear's designated branch,
   `feature/drc-3987-add-support-for-pi`. Do not implement on `main`.
2. Add a Pi store resolver with explicit precedence for the session-directory environment
   override, Pi configuration root, and readable global `sessionDir`. Keep it pure where practical
   and expose every effective candidate through `--diagnose`.
3. Add bounded Pi header and mutable-name metadata helpers. Validate the first record as a session
   header before treating arbitrary JSONL as a Pi session.
4. Add a defensive, branch-aware Pi transcript scan for the documented entry tree. It should
   rebuild the last persisted leaf-to-root path when an append changes branches, then derive
   prompts, tools, all output-usage shapes, and turn boundaries from that path only. Reuse the
   common rate, state, project, working-detail, and turn-progress presentation helpers.
5. Add a collector that scans both `*.jsonl` and `*/*.jsonl`, deduplicates by header ID, keeps
   forked/cloned sessions independent, and isolates per-file failures.
6. Register Pi in `HARNESSES`, `store_primaries()`, diagnostics, and the embedded JavaScript
   harness map.
7. Build the feature test-first from the criteria above, including flat overrides, name changes
   outside the tail, corrupt/partial files, duplicate IDs, future timestamps, and
   `parentSession`.
8. Reconcile `SKILL.md`, `README.md`, `COMPATIBILITY.md`, manifest descriptions, and durable
   design docs through the repository's `sync-docs` workflow, then run the complete AGENTS.md
   pre-PR suite.

After these criteria are confirmed, follow the feature workflow:
brainstorming → implementation plan → test-driven execution.
