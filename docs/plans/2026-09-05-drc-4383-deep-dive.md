operator's behalf to raise a session's terminal. No capability ships with it.

## The section's template, read off the git probe

What it does; the exact command or there is no command; why the mechanism differs and what each
flag is measured to prevent; what is published; what is never read; the cadence; the off switch and
its respawn behaviour; a closing violation sentence enumerating every bound.

B5 cannot inherit two of those. Its cadence is on demand, which is the exact thing the git probe
forbids itself. And its argv cannot be fully constant, because it carries a target. Closing those
two gaps is most of what the new section is for.

## Risks and open questions

- **The Scope violation sentence does not cover this, and evading it is worse than amending it.**
  Line 75 makes "running any program inside a user's repository other than the probe" a security
  bug. A focus command with no `cwd` set is outside that sentence on a technicality rather than on
  a boundary anyone reasoned about. DRC-4274's own triage note warned about this exact move: a
  promoted section landing under a clause that does not cover it.
- **DEC-11 (DRC-4342) is open, High, and disputes the sentence this section sits beside.** It asks
  whether SECURITY.md may keep claiming the git probe "neither writes there nor executes anything
  the repository supplies", after a reproduction showed a Git LFS filter attribute causing a
  `pre-push` hook to be installed. The generalizable lesson is the one B5 most needs: a bounded
  command can still cause a program to run through a path its flags never contemplated. A focus
  section written as though the git probe's claim were sound would inherit the same optimism.
- **Every other groundwork issue sits behind a filed decision; this one does not.** DEC-2 named B5
  as "the route to the same friction without a write power", which rules on write power. It does
  not rule on whether Cargento may execute a program on the operator's behalf outside a repository.
- **A second osascript caller, and the first whose script text is store-derived.** `notify_mac`
  escapes with a local `esc()` and has no bounds section. A focus path on macOS would be the second
  caller and the first taking an identifier out of an untrusted store.
- **Raising a window is the first action Cargento cannot undo and the user cannot attribute.**
  Every other action is idempotent and invisible outside Cargento. A raised window arrives with no
  provenance, and the row it came from is unverified in the way the ask lane already documents.
- **The platform matrix cannot be finished from what is measured.** DRC-4382 covers macOS
  Terminal.app and tmux. Wayland cannot be served at all, and Windows Terminal has no documented
  way to focus a tab.
- **The target is not stable and a device is not unique, both measured.** DRC-4382's verdict field
  is `identifier_shape_held_still` and deliberately does not claim the device itself held still; the
  tmux client device demonstrably moves on detach and reattach. And macOS recycles the device, which
  the capture caught: three Terminal tabs matched one device, one of them busy, because finished tabs
  still held a device handed out again. So a raise must resolve at raise time and decline an
  ambiguous answer. Neither was in the issue as filed.
- **Wayland and Windows Terminal are not in the capture.** The claims that Wayland cannot mint an
  activation token and that Windows Terminal cannot focus a tab came from desk research, not from
  anything in this repository, and the contract records them as research rather than relying on them.
- **Unknown unknowns.** The transitive trust of the multiplexer is the `core.fsmonitor` hazard in
  smaller form: tmux runs against a server whose config the operator owns. Nothing in the issue
  names it.
