# Deep Dive: DRC-4074 — the Gemini bucket now that Gemini CLI is retired

## Issue Summary

Gemini CLI was replaced by Antigravity CLI on 2026-06-18. Cargento carries one registry row keyed
`gemini`, labelled "Gemini", whose collector reads **both** the legacy Gemini CLI store and the
current Antigravity store. Decide what that row becomes, and apply the decision everywhere.

## Classification

**Type:** refactor (a rename/split with a decision attached, no new capability)
**Priority:** Low
**Status:** Backlog
**Branch:** `feature/drc-4074-harness-housekeeping-decide-the-gemini-buckets-fate-now-that` (does not exist)

## Two findings that change the ticket

### 1. The ticket's Option 3 would delete Antigravity support

`collectors/gemini.py` reads both store families and publishes both under one key:

| Line | Fact |
|---|---|
| `collectors/gemini.py:596-631` | legacy arm globs `gemini.tmp` |
| `collectors/gemini.py:678` | `out.extend(_collect_antigravity(...))` |
| `collectors/gemini.py:565` | Antigravity sessions call `base_session("gemini", ...)` |
| `collectors/gemini.py:658` | legacy sessions call `base_session("gemini", ...)` |
| `collectors/gemini.py:682-687` | `discover()` returns True if **either** store exists |

"Drop the registry row and collector" therefore removes the harness DRC-4070 targets. That option
is not viable as written and must be struck from the ticket.

### 2. The real drift is live, not legacy, and it is the inverse of what the ticket says

The ticket assumed the problem is stale legacy stores drawing a chip. The actual problem: a user
running **Antigravity today** sees their live sessions badged **"Gemini"** with the Google Gemini
star icon (`web/spark.js:261` `gemini:{code:"GE",name:"Gemini"}`, icon at `spark.js:250`). The
retired product's name and logo sit on the current product's sessions. Legacy Gemini rows are the
harmless half: nothing writes them, so they only appear under `?all=1`.

The merge was deliberate, and its stated reason has now expired. `collectors/gemini.py:1-7`:

> One registry key covers both source families: legacy Gemini CLI JSONL transcripts and current
> Antigravity CLI per-conversation SQLite stores. They share a discovery result, an error boundary
> and a display label, so they are one collector rather than two.

"They share a display label" was true when both products were Google's current Gemini surface. It
is what retirement broke.

## The collector's internal seam is clean

`collectors/gemini.py` is 688 lines holding two harnesses. The seam is exact:

- Lines 29-582: entirely Antigravity (`_root`, `_conversations_dir`, `_log_*`,
  `_session_metadata`, `_wal_has_data`, `_store_mtime`, `protobuf_*`, `_step_*`, `_session_info`,
  `_collect_antigravity`).
- Lines 583-687: the legacy arm plus `discover`. It calls **no** private helper from the block
  above except `_collect_antigravity` and `_conversations_dir` (the latter only inside `discover`).

So a module split is a move, not a rewrite. This also engages the architecture doc's own R-1 rule
("split it only if it holds more than one responsibility") rather than its rejected line-count rule.

## Options

**A. Split into two rows and two collector modules.** `gemini` (legacy JSONL) +
`antigravity` (current SQLite); move lines 29-582 into `collectors/antigravity.py`.
Breaks (all mechanical, each a reviewed one-liner): registry order list, import-graph allowlist,
runtime-file inventory, `fixtures.HARNESSES`, and the two assertions in
`test_gemini_antigravity.py`; the 24 Antigravity tests re-point to the new module. Harness count
9 -> 10. **Makes the byte-parity-enforced manifest description true with zero edits to it.**

**B. Split into two rows, keep one collector module.** Same user-visible result, smaller diff, but
leaves `AGENTS.md:28` ("one harness collector per file, one per supported harness") false.

**C. Relabel the single row to "Antigravity".** Smallest diff, no Python test breaks. But legacy
Gemini sessions would then badge "Antigravity", the published key `gemini` stays a lie, and the
four manifest descriptions (which list Gemini and Antigravity as peers) would each need editing:
precisely the byte-parity change sync-docs flags as risky.

**D. Keep one row; fix only docs and the label.** Cheapest. Antigravity users still see one chip
under one name, so the drift the issue exists to fix survives.

## Acceptance Criteria

1. Given a machine with only an Antigravity store, when the dashboard renders, then its sessions are
   labelled Antigravity (not Gemini) and the harness chip matches.
2. Given a machine with only a legacy Gemini store, when the dashboard renders with `?all=1`, then
   those sessions still appear and are labelled as Gemini.
3. Given `GEMINI_CLI_HOME` is set, when stores resolve, then both `gemini.tmp` and
   `antigravity.root` still relocate under it (`test_config_diagnostics.py:593-597` stays green).
4. Given the Python registry, when the frontend `HARNESS` map is compared to it, then a new test
   fails on any key or label mismatch.
5. Every stated harness count in the repository agrees with the registry, and the false "ten"/"eight"
   claims above are corrected.
6. The decision and its reasoning are recorded in a design doc, replacing the now-expired
   "they share a display label" rationale in the collector docstring.
7. The quality gate passes.

## Risks and Open Questions

- **A new published harness key is a payload change.** `harness: "antigravity"` is new in
  `/api/data`. The page's per-session rate history is keyed `harness:sid`, so existing Antigravity
  rows lose their in-browser rate buffer once (self-healing on the next poll). Display ids may also
  shift for those sessions. Cosmetic, but real.
- **The `antigravity` row would have no environment variable of its own.** It stays relocated by
  `GEMINI_CLI_HOME` (`config.py:138`). Adding `ANTIGRAVITY_HOME` would change `STORE_ENV_VARS` and
  the doc-matches-code equality assertion: a separate decision, deliberately out of scope here.
- **Do not conflate the two meanings of "gemini".** Cargento *ships to* Gemini CLI as a host
  (`cargento/gemini-extension.json`, `validate_gemini_extension`, `bump_version.py`). None of that
  moves. Only the monitored-harness references do.
- **`turns.py`'s `harness == "gemini"` dispatch must keep receiving `"gemini"`** from the legacy arm.
  It selects Gemini JSONL record expansion; Antigravity never reaches `scan_turns`, so nothing there
  should be renamed to `"antigravity"`.
- Historical text stays: the DEC-1 survey in DRC-4053 and dated design-doc statements describe what
  was true then. Only outright false counts are errors rather than history.

## Proposed Approach

Option A, in one PR (the count changes are caused by the split, so splitting them across PRs leaves
main internally inconsistent). Order: registry and module split with tests green, then the frontend
entry plus the new parity test, then the doc and count sweep, then `/sync-docs`.
